# 04 — Synthetic rendering, pixel metrics and visual limitations

**Code:** `lib/geometry/raster.js` and `app/manual/preview.js`.
**Status:** a deterministic explanatory raster, not the native CS2 renderer.

## 1. Why there is a renderer in a math project

Numerical dimensions are necessary but can conceal shape and placement mistakes. A
preview makes the selected model inspectable: are the arms the expected length, is a
dot actually present, and does changing the gap move the intended edge? It is useful
for debugging the model and configuration workflow.

It is not an independent ground-truth test. When both the old reference and new candidate
are generated by project code, agreement demonstrates consistency under those code paths.
It cannot discover a missing native effect that neither path implements. This is why
both canvases and the mask readout explicitly call themselves models or simulations.

## 2. Half-open rectangle construction

The current illustrative placement is `illustrative-parity-v2`. Given arm length $L$,
width $W$, near drawing edge $a$, and far drawing edge $b$, define transverse start

$$
t=-\lfloor W/2\rfloor.
$$

The legacy and forward-model `near`/`far` fields retain their original arithmetic
offsets. For synthetic drawing, `a = near`; `b = far - 1` for even integer widths
and `b = far` otherwise. Even bars straddle a pixel boundary, while odd bars have
a center pixel. Applying the extra center-pixel offset to both produced the visible
right/down displacement in v1. Fractional widths retain the prior sampling rule;
this is an illustrative convention, not a claim about native subpixel rendering.

The illustrative rectangles are

$$
\begin{aligned}
R_{\text{left}}&=[-a-L,-a)\times[t,t+W),\\
R_{\text{right}}&=[b,b+L)\times[t,t+W),\\
R_{\text{top}}&=[t,t+W)\times[-a-L,-a),\\
R_{\text{bottom}}&=[t,t+W)\times[b,b+L).
\end{aligned}
$$

The dot is $[t,t+W)\times[t,t+W)$. T style omits only the top arm. If $L=0$, no arms are
created; a dot can still exist. Half-open intervals avoid an accidental extra pixel
from treating both endpoints as inclusive.

The centering rule is a declared illustration assumption, tested by literal pixel
fixtures. It is not native validation. Version 1 drew the unadjusted far offset
for every width; version 2 fixes even-width alignment. Original measured masks are
never shifted. Their independently extracted edges use `measured-edges-v1` when
reconstructed, as do the manual lab’s scoped affine predictions.

The dense preview and analytical union loss share the same rectangle builder.
Reports identify the convention and show drawing edges separately from formula
offsets. The inverse certificate still covers the raw formula objective; visual
refinement uses the drawn cells. Native calibration and holdout checks compare
measured edges with the predicted drawing edges. Changing the illustration can
therefore change shape scores, rankings, and conditional weights, without supplying
new native evidence. Old screenshot templates also identify this convention.

Screen-relative fractional targets apply this rule after dimension scaling; they
do not claim to reproduce resampling of an original image. Imported image masks
remain unchanged and cannot be silently rescaled.

## 3. Sampling and finite inspection windows

The binary mask samples each pixel cell at its center. For a one-dimensional half-open
interval $[x,x+w)$, a cell with integer index $i$ is covered when

$$
x\le i+\tfrac12<x+w.
$$

This becomes the integer range from $\lceil x-1/2\rceil$ inclusive to
$\lceil x+w-1/2\rceil$ exclusive. Integer rectangles therefore produce the expected
integer cell counts, while fractional research hypotheses have a deterministic but
explicitly illustrative rasterization.

Masks use an odd 161-by-161 inspection window by default. Larger shapes may extend
outside it; the `cropped` flag disables whole-shape agreement claims in the UI. The
core accepts bounded odd windows up to 513. These caps control memory and drawing work.
They do not limit the arithmetic source model to 161-pixel-wide crosshairs.

Do not interpret matching cropped masks as matching whole crosshairs. Do not interpret
matching empty masks as a useful aiming configuration. With no arms and no dot, the
shape contains no colored geometry; the converter warns accordingly.

## 4. What the difference view measures

For binary masks $A$ and $B$, the comparison reports

$$
N_{\ne}=\sum_{i,j}[A_{ij}\ne B_{ij}],
$$

and, when the union is nonempty,

$$
\operatorname{IoU}=\frac{|A\cap B|}{|A\cup B|}.
$$

An empty union has undefined IoU in this tool, represented as `null`, not a flattering
100% score. The UI's main readout uses differing pixels rather than presenting an
unqualified accuracy percentage. If the mask is cropped, it says so.

The difference canvas uses one color for overlap and distinct colors for new-only and
old-only regions. Those colors are diagnostic labels, not crosshair-color suggestions.
The metric excludes color, opacity, outline, dynamic motion and real game rendering.
A zero value cannot validate any of those omitted dimensions.

For a screen-relative cross-resolution target, comparing the old unscaled mask to a new
mask is not the stated mathematical objective. The UI therefore directs the user to
numeric target residuals instead of presenting a same-pixel agreement claim. The two
canvases retain their explicit source/target heights.

## 5. Zoom, device scale and stretching

The canvas magnifies game-model pixels for inspection. It uses a bounded pixel mask,
nearest-looking filled cells and no smoothing of the mask itself. Browser device-pixel
ratio is handled when allocating the canvas backing store so text-independent raster
content remains reasonably crisp on high-density displays. Fractional CSS layout or
an emulated stretch can still place boundaries between physical display pixels.

A 12× canvas zoom means twelve CSS units per modeled game pixel before any horizontal
stretch. It is not a claim about the game's pixel density. The “4:3 → 16:9” view applies
a horizontal display factor of $4/3$ to both previews. It never changes the candidate
numbers or exported configuration.

If the old and new game images use different aspect treatments, one scalar length or
thickness setting generally cannot undo independent horizontal and vertical scaling.
Preserve the same stretched/black-bars mode for an initial equivalence experiment.
Measure native captures before the display transform when possible and record exactly
which image space a screenshot represents.

## 6. Color presets and opacity

The old reconstruction resolves preset RGB values as follows:

| Old color index | RGB |
|---:|---|
| 0 | 250, 50, 50 |
| 1 | 50, 250, 50 |
| 2 | 250, 250, 50 |
| 3 | 50, 50, 250 |
| 4 | 50, 250, 250 |
| 5 | Custom RGB settings |

This mapping comes from [S01](../research/source-ledger.md#s01-old-static-geometry), not
an assumption that named colors are pure 0/255 primaries. A legacy preset can ignore
stored custom RGB fields. Resolve the preset before copying numbers into the new RGB
variables. The color picker switches the source settings to explicit custom RGB.

When old alpha is enabled, copy its numeric alpha into the new alpha component as a
candidate. When old alpha is disabled, the source reconstruction uses a fallback of
200, not 255. This is implemented and tested as a source-derived rule. It remains a
separate native blending question, especially over backgrounds with different colors.

Canvas compositing uses its own normal alpha treatment over the lab background. It does
not implement CS2's entire HUD compositing pipeline, gamma path or possible native
premultiplication details. Equal alpha numbers alone do not prove equal displayed color.

## 7. Outlines and dots

The old inventory has a separate outline width; the inspected new inventory does not
expose an equivalent standalone setting. The new outline toggle remains. The converter
therefore carries the toggle, but does not pretend to map a legacy custom outline width
through the arm-length factor.

The preview draws a one-pixel expanded black border for illustration, then the colored
core. That is not a verified implementation of native outline joins, overlapping alpha
or antialiasing. The geometry-mask score ignores it. Turn outlines off when calibrating
the core geometry, then assess the outline separately.

Dot-only legacy constructions are kept as style 4 plus zero arm length and an enabled
dot. The new style-6 Dot Only option exists in the inventory, but identical native shape
and alignment have not been established. Automatically switching styles to make the
settings look cleaner would introduce an untested change. The current native designer
likewise creates its dot within the supported static construction.

## 8. Dynamic and contextual behavior

A dynamic crosshair is a function of time and game state, not just a static parameter
vector. The new inventory enumerates multiple dynamic styles and a spread-limit setting.
Those names and descriptions do not provide the full motion, spread or weapon-state
function. This project does not simulate them.

Legacy styles other than 4 and weapon-dependent gap are blocked for conversion exports.
Follow recoil can be retained as a preference, but only the at-rest shape is previewed
and that limitation is surfaced. Sniper scope width, grenade crosshairs and teammate
warning overlays are not included in the equivalence claim or overwritten by the
candidate exporter.

Static preview agreement should never be generalized to moving, firing, changing weapon,
spectating or scope transitions. A future dynamic model needs stateful reference traces
and its own acceptance criteria.

## 9. When exact reproduction is not representable

An old crosshair may request overlapping bars, an outline width no longer exposed, a
negative effective gap, fractional geometry unavailable in the chosen integer controls,
a parity offset absent from the new model, or independent horizontal/vertical transforms.
A nonempty solution set is not guaranteed.

The honest output is then a nearest legal candidate with residuals and an explanation
of which property cannot be preserved—not a forged universal conversion. A user may
prefer one approximation over another for gameplay, but that preference does not change
the geometry or establish a native mapping. Keep the quantitative residual and visual
judgment separate.
