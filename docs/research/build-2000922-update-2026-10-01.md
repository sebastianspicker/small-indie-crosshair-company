# Build 2000922 crosshair update — October 1, 2026

Valve's October 1 update changed the crosshair again. Public tracker build
**2000922** (committed September 30, 23:56 UTC, `PatchVersion` 1.41.8.8)
differs from the inspected build **2000918** in convar ranges, a new style, new
outline-colour cvars, a rewritten crosshair shader and a replaced native
renderer class. The app advances to `community-static-v4` and community model
id `community-static-2026-10` (release 0.9.0). The v4 forward equations are
**unchanged from v3**; applying them to build 2000922 is an unverified
carry-over across a renderer rewrite. There are still no native old/new capture
pairs in this repository.

Evidence here is metadata, a shader diff and a vendor changelog. None of it
reveals the compiled CPU-side layout that now places the HUD crosshair.

## Shader and renderer analysis

The shader `Version` constant moves from 0 to 2. Verified differences:

- **Tiled rendering.** Primitives are binned per tile with a 64-bit per-tile
  mask, allowing 64 primitives; the old shader looped over 16 entries.
- **New primitive types.** Type 3 (glyph atlas) and type 4 (friendly icon),
  composited additively. They add overlay content, not bar geometry.
- **Unchanged.** The rectangle plus outline coverage path (inclusive integer
  bounds `[xy, zw]`, outline expansion by `m3.x`/`m3.y`) and the circle paths.

`client_strings.txt` replaces `CCSGO_Crosshair` / `csgo_crosshair.cpp` with
`CCSGO_CrosshairPreview` / `csgo_crosshair_preview.cpp`, now only the settings
preview, and adds `CCsgoCrosshairTileRenderer` and `CsgoCrosshairLayout`. HUD
layout therefore moved to a native renderer.

**What this supports:** the per-pixel coverage of a rectangle with an outline
is, by the shader's source, the same integer-bounds rule as before.

**What it does not support:** that the CPU code deciding those bounds (rounding
of authored-to-current scaling, gap origin, odd/even centring, minimum
thickness, negative-gap overlap) is unchanged. That code is compiled and not
observable here. The shader being unchanged for rectangles is also not
evidence about the layout stage that feeds it.

## Decisions

- **Model.** `community-static-v4`, community model id `community-static-2026-10`,
  build 2000922. Forward equations equal v3 and are labelled an unverified
  carry-over across the renderer rewrite. No native capture pairs exist.
- **Thickness.** Search and clamp maximum 32.
- **Gap.** The Static Cross export and search range stays 0..128, following the
  UI slider and the changelog scope. An old gap that would need overlap (negative
  centre radius) clamps to 0 and raises the new warning `negative-gap-static-unverified`.
- **CFG exports.** Every automatic and manual export also emits
  `cl_crosshairoutline_r 0`, `_g 0`, `_b 0` and `_a 255`. Legacy outlines were
  opaque black; this pins a custom outline colour left in a player's config.
- **Historical models** (`quant-static-v6`, manual `conditional-static-v4`,
  the 2000914 inventory) are unchanged.
- **Measurement intake.** Build 2000918 records are rejected with a re-capture
  message. Build 2000922 native records may carry any gap the cvar accepts
  (-3840..3840). Captures with a gap outside the static range 0..128 are
  reported as outside the model domain (`negative-gap` or
  `gap-above-static-range`) and excluded from holdout validation until a model
  covers them.
- **Import.** New-build cvar names, including the outline colour, are rejected
  on legacy import. Non-v1 share codes remain unsupported; there are now three
  formats: legacy v1, September 22 2026 and October 1 2026.
- **Learning.** The accuracy and structured learners, whose labels come from
  the current solver, were retrained on v4 labels with the unchanged protocol,
  seeds and capacity grids. This is a regression re-run on already-observed
  groups, not fresh holdout evidence, and it does not enter the runtime. The
  community emulator distills the frozen v2 reference; it keeps its 31-pixel
  thickness domain and its artifact is byte-identical.

### Effect of v4 on the learners

v4 changes 1,152 of 15,360 accuracy-experiment labels (train 468, validation
100, calibration 144, test 152, interior 60, exterior 228), every one a
thickness of 31 becoming 32 on saturated thick crosshairs. Exact-tuple fidelity,
v3 labels → v4 labels:

| Experiment / predictor | Test | Interior | Exterior |
| --- | ---: | ---: | ---: |
| Accuracy: frozen analytic baseline | 81.82% → 75.93% | 62.81% → 59.06% | 75.16% → 64.22% |
| Accuracy: residual | 96.31% → 95.21% | 52.97% → 51.48% | 63.59% → 57.89% |
| Accuracy: quantization-aware | 97.29% → 96.99% | 73.91% → 69.92% | 77.66% → 77.89% |
| Structured: canonical arithmetic | 91.58% → 92.25% | 67.27% → 66.95% | 94.14% → 94.14% |
| Structured: residual + projection | 97.75% → 97.83% | 73.36% → 78.67% | 95.70% → 94.92% |
| Structured: candidate ranker | 98.75% → 98.50% | 84.22% → 83.91% | 96.02% → 96.09% |

The frozen analytic and v2-residual baselines clamp thickness at 31 and cannot
express the new labels, which explains most of their drop. Structured candidate
recall stays 100% on every split. Ranker rescue/damage against the same-data
residual is now 35/9 on test (was 37/3), 353/88 interior and 250/10 exterior.
Interior intervals still accept 8/80 complete groups for the accuracy learner,
but accepted-row coverage falls from 100% to 96.86% (quantization-aware) and
95.54% (residual); exterior still abstains entirely. These are solver-imitation
results only.

## What the evidence does not support

- Native pixel accuracy of v4 on build 2000922 for any setting.
- Behaviour of negative gaps on Static Cross or on any style other than classic
  dynamic. The cvar range permits them; the UI and changelog do not.
- Appearance of Static Quadrant, Dynamic Quadrant, grenade-in-freeze-time or
  the outline colour beyond the exported cvar values.
- The new share-code layout.
- That the unchanged rectangle shader implies unchanged layout arithmetic.

## Open questions

1. Does the native layout still round, centre and place gaps as v3 assumes?
2. How does Static Cross render a negative gap set via console (0..128 UI)?
3. Is a thickness 32 bar rendered at full width, or does an odd/even rule change?
4. Does an exported config with `cl_crosshairoutline_a 255` and black RGB
   reproduce the old opaque black outline exactly?
5. Is the 2000922 outline opacity independent of `cl_crosshaircolor_a`, or scaled
   by it? Old outlines used the crosshair opacity (S01), so the export keeps 255
   and warns below full opacity.
6. Does the half outline (`cl_crosshair_drawoutline 2`) match an old outline
   width below 1? Old outline rectangles truncated to whole pixels, which widens
   only the top and left edges for widths between 0 and 1 (issue #11).

## Native capture protocol

Superseded and extended by the [October 2 protocol](capture-protocol-2026-10-02.md); the steps below remain valid.

Purpose: decide questions 1 to 5 (question 6 needs pre-update captures). Choose the calibration/holdout role of every
capture **before** measuring, per the
[measurement policy](../evidence/measurement-policy.md) and the
[calibration protocol](../math/03-calibration-protocol.md).

Setup: build 2000922 (record `steam.inf` / in-game version), native 1920x1080,
no scaling, a static map position with a flat neutral background, HUD scale
default, and the crosshair at `cl_crosshair_screen_height 1080`.

1. Style 4, length 8, outline off, colour opaque white. Thickness 1 and 2
   (odd/even). For each thickness capture gaps 4, 0, -1, -3 and -4 (10
   captures). Negative gaps are set from the console and are outside the
   documented UI range for this style; record that.
2. One capture at thickness 32 (style 4, length 8, gap 4).
3. Run the app's exported cfg with an outline enabled after first setting a
   custom outline colour in game; capture once. The cfg must reset the colour
   to opaque black. Capture the same settings with no exported cfg as control.
4. Outline on, `cl_crosshaircolor_a 128`: capture once with
   `cl_crosshairoutline_a 255` and once with `128` to decide question 5.

Record each as a `native-user` observation (kind), with the capture's SHA-256,
the build and resolution, the exact cvar values, and an attestation that the
capture is an unedited native screenshot. Store the file outside the repository
or note its location; entries enter only via the measurement import. Imported
records remain user-attested, are never silently promoted to validation and
should be reviewed separately before they count as native evidence.

## 2026-10-02 addendum

Evidence labels: **verified** (read directly in a pinned file), **inferred**

### Game dumps (SteamDatabase/GameTracking-CS2)

- **Builds.** The last pre-update build is 2000908 (`d8e2c7a`, 2026-09-09); an older
  reference is 2000856 (`39aa58f`). The crosshair convars, panorama files and strings
  are identical back to 2000691. [verified]
- **No crosshair shader before the update.** `materials/dev/csgo_crosshair.vmat_c`
  first appears at `10f3693` (2000913); `shaders/vfx/csgo_crosshair.slang` is first
  dumped at `18d0779` (2000915, 237 lines) and has 428 lines at `6ac2479` (2000922).
  [verified] Our old-renderer model therefore stays the leaked CS:GO source below;
  there is no pre-update shader to switch to.
- **The old HUD crosshair was a Panorama panel.** `CCSGO_Crosshair::Paint` drew integer
  rects (signature `void(void*, int x8, float, bool)`). `hudreticle.xml` hosted
  `<CSGOCrosshair>` until 2000921, when it was removed in favour of the native
  `CCsgoCrosshairTileRenderer` (128 px tiles). [verified; the link between the two is
  inferred]
- **Shader, rectangle primitive.** Fill is `p >= xy && p <= zw` (inclusive integer
  bounds). The outline is `p >= xy - m3.x && p <= zw + m3.y`: the minimum and maximum
  corners expand separately, consistent with the half outline being top-left
  [inferred]. A fractional `m3` acts as a floor on integer pixels, so any rounding is
  on the CPU. Outline alpha is independent of fill alpha in the shader. Primitive types
  are 0 rect, 1 ring, 2 quadrant ring, 3 glyph, 4 friendly icon; there is no
  hollow-rectangle primitive. [verified]
- **Open.** `int2(gl_FragCoord.xy - m1)` truncation may produce a one-pixel left/top
  asymmetry. Whether a zero-length bar is an empty rect (so an outline-only result is
  possible) or a 1 px rect is unknown.
- **Removed names survive as strings.** `cl_crosshair_outlinethickness`,
  `cl_crosshaircolor`, `cl_crosshairgap`, `cl_crosshairgap_useweaponvalue` and
  `cl_fixedcrosshairgap` remain as string literals in `client_strings.txt` from 2000913,
  which suggests in-game migration of old values [inferred]. Hidden convars
  `cl_crosshairsize` (3.9), `cl_crosshairthickness` (0.6) and `cl_crosshairalpha` (200)
  remain. `ImportCSGO` was removed at 2000913. [verified]
- **Per-weapon gap removed.** `weapons.vdata` `m_nCrosshairMinDistance` (values
  0, 3, 4, 5, 6, 7, 8, 9; 4 is the most common at 45 of 174) and
  `m_nCrosshairDeltaDistance` were removed at 2000913. [verified] This is why the
  per-weapon gap option stays blocked. [inferred]
- **Workshop whitelist.** A transient `workshop_whitelisted` flag on the crosshair
  convars at 2000916/917. [verified]
- **Tracker flap.** `3b5862a` (2000921) and `42d0ddd` (labelled 2000919, which
  reverts) are interleaved. [verified]
- **Share codes.** Both post-update example codes are `CSGO-` with version byte 3, but
  their payload layouts differ (2000913 against 2000921). [verified]
- **UI per style** (`settingsmenu_crosshair.js`). [verified]

  | Style | Controls |
  | --- | --- |
  | 0 | dot, gap 0..128, length, T, spread limit |
  | 1 | dot, spread limit |
  | 2 | dot, classic gap -10..128, length, T, split sliders |

  | 4, 5 | dot, gap, length, T |
  | 6 | nothing |
